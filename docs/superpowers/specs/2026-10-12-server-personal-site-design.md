# 个人网站服务器改造设计

日期：2026-10-12
状态：方案已获口头同意；本文供实施前审阅。

## 1. 已确认的目标与环境

- 保留现有毛玻璃风格及文章、杂谈、说说、照片墙、友链、项目、音乐、关于和灵境页面。
- 将后台部署到服务器，在浏览器中登录后管理内容和配置。
- 第一阶段通过公网 IP 测试，没有域名；公开访问地址计划为 `http://8.133.165.170:8080`。
- 服务器为 Ubuntu 24.04.2、x86_64、2 核、约 1.6 GB RAM、2 GB Swap、剩余磁盘约 30 GB。
- Docker、Docker Compose、Nginx 已安装。使用 admin 账号及专用 SSH 密钥连接。
- 现有 Nginx 80 端口服务 `/var/www/training`，API 转发到 127.0.0.1:5000；保持其配置与服务。
- 本机 `.venv` 使用 Python 3.14.7，目前只安装了 pip；服务器 Python 为 3.12.3。
- 仓库根目录目前没有 Git 元数据，不运行破坏性更新器，也不假设存在可回退的提交。

## 2. 架构选择

选择一套 Next.js 网站加一个内部 FastAPI 内容服务，部署为独立 Compose 项目。

- `XHBlogs` 是生产网站入口，保留访客页面，将现有管理端的编辑器与设置功能迁移到 `/admin` 下。
- `my-blog-manager/cms_core` 改为独立内容服务，不依赖 pywebview 或 Windows 启动脚本。
- 避免在小内存服务器同时运行两套重复的 Next.js 网站；旧桌面入口不作为生产部署入口。
- 浏览器使用同源相对地址 `/api/cms/...`，由 Next.js 受控代理转发到内部 FastAPI 服务。
- 代理限制路由、请求体大小和超时；不对外提供 SSH、Git shell、任意目录同步或源码更新接口。
- FastAPI 自行校验会话和请求类型，不能只依赖前端导航隐藏管理员入口。
- 公共音乐、天气和 AI 接口继续由 Next.js 提供；采用独立的输入限制、超时和错误处理。

## 3. 数据与发布

### 持久化目录

独立应用目录计划为 `/opt/xhblogs`，先确认未被其他项目使用。
内容和上传数据放在该目录下的持久化目录，代码镜像与内容数据独立。

内容目录包含：

- `posts/`、`chatters/`、`moments/`：Markdown 与 YAML Front Matter。
- `about.md`：关于内容。
- `drafts/`：草稿 JSON。
- `site.json`：公开站点配置。
- `albums.json`、`friends.json`、`projects.json`：结构化数据。
- `uploads/`：本地图片。

认证信息和图床等密钥存放在独立的服务端秘密目录或环境变量中，不挂载给公共网站，不进入客户端配置。

### 迁移规则

- 优先导入管理端现有内容，展示端中不同或独有的内容另存迁移备份并输出差异清单。
- 不因同名文件直接覆盖或删除原始内容；保留两端原文件。
- 不执行任意 TypeScript 代码来解析配置，使用有边界的迁移解析器和类型校验。
- 迁移使用版本标记，重复启动不重复导入，不重置用户修改。
- 原子写入采用同文件系统临时文件加替换；对多文件操作加锁，删除先移到可恢复目录。
- 对内容 ID、文件扩展名和解析后的绝对路径进行验证；拒绝目录分隔符、路径穿越与逃逸的符号链接。

### 发布行为

- 草稿和已发布内容明确分开，保存草稿不修改公开文章。
- 发布先校验完整数据，再写入并使对应页面读取到新数据。
- 内容和公开配置使用运行时读取，避免依赖构建时导入的 TypeScript 常量。
- 公共页面的静态化、动态读取与缓存策略明确配置；正常发布不要求重新构建整个站点。
- 前端操作队列统一使用带类型的操作结构，以内容 ID 去重，记录每项完成或失败结果。
- 刷新后恢复待处理操作；成功任务从队列移除，重试不重复创建文章。
- 不把密码、密钥或登录会话写入前端持久化队列。

## 4. 管理与安全

- 单管理员登录；初始密码通过专用初始化工具设置，保存加盐密码哈希，不提供默认密码。
- 使用签名会话、HttpOnly Cookie、有效期、注销机制和登录失败限制。
- 管理接口验证身份与写操作来源，防止 CSRF；公网请求不能直接访问内部内容服务。
- 公共配置使用显式字段白名单；图床 Token、OAuth Secret、AI Key 永远仅用于服务端调用。
- 评论 OAuth 转换由服务端填充 Secret；验证回调流程，不把 Secret 交给 Gitalk 浏览器组件。
- Markdown 输出加入 HTML 清洗，兼容代码、表格、数学公式与允许的图片结构。
- 图片上传限制类型和大小，使用服务端生成文件名；远程图床地址限制协议和目标，防止请求内网资源。
- AI 请求限制长度、频率、输出量和调用时长；未配置密钥时显示可理解的禁用状态。
- 音乐、天气、评论等第三方服务无法成功时提供降级提示，不把第三方凭据缺失视为整个网站启动失败。

### 公网 IP 测试阶段

HTTP 公开入口只用于访客浏览；管理员操作通过 SSH 隧道的本机入口完成，防止在公网明文传输管理员密码和会话。
部署脚本提供建立隧道的命令及本机后台地址。
域名和 HTTPS 就绪后，可切换为公开 HTTPS 后台并启用 Secure Cookie，无需重建内容数据。
代理不会仅凭浏览器可伪造的转发头认定请求来自管理隧道。

## 5. 部署与运维

- 单独的 Compose 项目和应用目录；不替换已有站点或占用 80、5000 端口。
- 网站服务发布到服务器环回地址，Nginx 新增独立 8080 入口；内部 API 无公网端口。
- 设置独立的环回管理入口供 SSH 隧道使用；公共入口阻止管理页面及管理 API。
- 验证现有 Nginx 配置，新增配置后先 `nginx -t`，通过后平滑 reload。
- 优先检查本机是否支持 Linux 镜像构建；若不可用，在服务器按顺序受控构建，限制并行度并监测内存、Swap、磁盘与现有服务。
- 不随意调整现有服务资源，也不一次并行构建多个 Node 项目。
- 应用容器设置自动重启与健康检查；运行进程使用非 root 用户，限制日志体积。
- 提供 `.env.example`、生产 Compose、Dockerfile、Nginx 示例、部署与更新脚本。
- 阿里云安全组只需按需开放 8080；若没有云控制台权限，由用户完成此项，不宣称已开放。
- 备份包含内容、上传与服务端配置，使用独立备份目录；提供恢复工具及更新失败回退步骤。
- 不通过现有 `update.py` 覆盖部署后的项目；代码更新走可回退的构建和发布流程。

## 6. 工程修复范围

- 恢复生产入口的 TypeScript 检查；修复新架构涉及的现有类型与依赖错误。
- 修复富文本与 Markdown 往返转换，保留标题、链接、引用、列表、代码、表格和数学内容。
- 安全隔离或移除生产中的旧 Git 推送、危险同步和更新入口。
- Windows 桌面启动脚本修复版本检测；桌面运行不是服务器正常工作的前提。
- 明确旧目录用途、迁移步骤和新入口，避免两套网站继续产生不同的内容副本。
- 增加文章独立标题与描述、站点 URL 配置、sitemap 和 robots；后台不进入搜索索引。
- 3D 与背景动画按需加载，提供低性能设备的降级方式；先保持功能，再根据实测调整。
- 不替用户编造个人信息，不申请外部账号，不自动配置未知的第三方密钥。

## 7. 验证与验收

本机：

1. 使用项目虚拟环境安装并检查 API 依赖，记录 Python 3.14 兼容情况；生产 Python 3.12 单独验证。
2. 生产入口类型检查、Lint 和生产构建通过。
3. 后端关键测试覆盖身份校验、路径穿越、配置读写、发布幂等、草稿隔离、原子写入和 HTML 清洗。
4. 编辑器往返样例覆盖常见文章格式，不只检测页面是否返回 200。
5. 验证迁移可重复运行且不覆盖已修改的内容。

服务器：

1. 首页与所有保留的内容页面可访问，浏览器无阻止主流程的错误。
2. 管理员能登录、保存草稿、重新编辑、发布、删除和修改站点设置，公共页面随之更新。
3. 未登录访问管理操作失败；公共入口不能访问内部 API 或管理员秘密。
4. 服务重启、容器重建和一次更新后内容仍保留；备份能在隔离目录恢复。
5. 保持已有 80 端口站点可用；验证资源占用和日志。
6. 从外部检查 8080 的真实可达性，不把本机环回成功当作公网部署成功。
7. 对第三方功能逐项注明已验证、缺少凭据或外部服务异常。

## 8. 实施阶段与交付

按顺序实施：环境与基线检查 → 内容服务及迁移 → 登录与同源管理 API → 网站运行时数据与后台迁移 → 构建与功能验证 → 服务器部署和恢复验证。

交付包括修改后的源码、测试结果、部署文件、实际访问方式、迁移差异清单、备份恢复工具、环境变量说明和更新文档。
完成标准是核心管理与发布流程经过验证，服务器入口真实可访问，旧站点和用户内容保持完整。
